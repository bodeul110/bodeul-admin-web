# 무통장입금 Preview 상태 전이 검증

기준일: 2026-09-06

## 작업 판단

- 작업 목적: 실제 Firebase 인증, 관리자 서버, 개발 PostgreSQL을 거치는 무통장입금 상태 전이와 중복·충돌 처리를 확인한다.
- 선택한 방식: 검토·병합된 관리자 웹 코드로 검증용 Preview를 만들고, 그 배포에만 서버 쓰기 플래그를 적용한다. 개발 Core API로 새 합성 예약 두 건을 생성해 정상 입금과 취소 후 지연 입금을 나누어 검증한다.
- 대안: Preview 공통 환경변수 변경, 기존 취소 예약 재사용, 관리자 DB 직접 UPDATE는 선택하지 않는다.
- 선택 이유: 현재 MVP에서는 기존 정상 동작과 비교 가능한 두 시나리오면 상태 계약을 검증할 수 있다. 배포 단위 설정과 합성 예약을 쓰면 다른 Preview나 기존 데이터의 영향을 줄일 수 있다.
- 리스크: 개발 환경도 실제 DB 쓰기와 감사 저장이 발생한다. 실행 전 환경·배포·대상 식별을 확인하고, 응답이 불명확하면 새 작업을 만들지 않고 원장과 기존 작업 ID부터 대조한다.

## 실행 전 조건

- [메인 #407](https://github.com/bodeul110/Bodeul/pull/407)의 V23 적용, 최초 개발 관리자 배정, 조회 200·일반 사용자 403·쓰기 잠금 423 기록을 확인한다.
- 검증 배포는 정확한 프로젝트의 Preview이며 `READY`여야 한다. `BLOCKED`, `ERROR`, `BUILDING`에서는 예약 생성과 결제 변경을 시작하지 않는다.
- `ADMIN_BANK_TRANSFER_WRITES_ENABLED=true`는 해당 배포에만 전달한다. 공통 Preview 환경변수와 Production 설정은 변경하지 않는다.
- Firebase 개발 프로젝트와 Core API Preview를 대조하고 정상 ID token으로 인증한다. Deployment Protection을 끄거나 인증 코드를 대체하지 않는다.
- 기존 사용자·예약·원장·이벤트의 건수와 비교값을 확보한다. 인증·계좌·개인정보는 로그와 공개 기록에 남기지 않는다.

## 합성 시나리오

| 구분 | 확인할 흐름 | 기대 결과 |
| --- | --- | --- |
| 정상 입금 | 새 예약 생성, 입금자명 등록, 입금 확인, 환불 요청·완료 | 서버가 반환한 예상 금액을 사용하고 상태·버전·감사가 한 번씩 증가 |
| 취소 후 입금 | 별도 새 예약 생성·취소, 검토 필요, 환불 요청·완료 | 취소 예약의 입금 확인은 거부하고 환불 경로만 허용 |
| 중복 요청 | 같은 작업 ID·버전·본문 재전송 | 성공 응답, 변경 이벤트·UPDATE 감사·버전 중복 증가 없음 |
| 작업 충돌 | 같은 작업 ID에 다른 본문 또는 다른 예약 사용 | 409, 원장 변경 없음 |
| 버전 충돌 | 오래된 버전과 새로운 작업 ID | 409, 원장 변경 없음 |
| 금액·순서 오류 | 불일치 금액, 입금자명 미등록, 허용되지 않는 상태 순서 | 400 또는 409, 실패를 성공으로 표시하지 않음 |
| 일반 사용자 | 환자·보호자의 관리자 조회·변경 요청 | 403, 관리자 처리 권한 없음 |
| 종료 확인 | 최종 환불 상태 조회, 다른 기존 예약 비교 | 합성 이력 보존, 기존 데이터 불변 |

금액·입금 확인·환불은 합성 상태 기록이며 은행 송금이나 실제 환불을 실행하지 않는다. 검증 사유에도 합성 검증임을 표시한다. 화면·HTTP·DB 결과는 각각 구분한다.

## 정리와 재실행

검증을 마치면 쓰기를 허용한 임시 배포를 제거하고 기존 읽기 전용 Preview와 Production을 그대로 유지한다. 실패한 배포도 실행 가능 여부를 확인해 정리한다. 합성 예약·원장·이벤트·감사는 임의 삭제하지 않는다.

다시 실행할 때는 기존 실행 식별자와 완료 단계를 먼저 확인한다. 통신 실패 뒤 예약 생성 ID나 결제 작업 ID를 새로 발급해 중복 처리를 만들지 않는다. 원격 상태 변경이 시작되지 않은 실행과 일부 반영된 실행을 구분한다.

## 2026-09-05 배포 차단 기록

배포 source dry-run에서 추적된 파일만 포함되고 로컬 환경변수·인증 파일은 포함되지 않음을 확인했다. 첫 배포와 인증된 본인 계정의 ID 기반 noreply 이메일을 사용한 새 문서 커밋 배포가 모두 빌드 전 `BLOCKED`였다. 사용자 화면에서도 커밋 이메일과 Git 계정 불일치 안내를 확인했다. CLI의 종료 코드 0·ready 문구와 달리 실제 배포 상태는 성공이 아니었다.

기존 병합 커밋의 작성자는 GitHub API에서 본인 계정으로 인식됐다. 이메일 표기만 바꾼 새 커밋도 동일하게 차단됐으므로 [Vercel 협업 계정 기준](https://vercel.com/docs/deployments/troubleshoot-project-collaboration)에 따라 프로젝트 소유 계정의 GitHub Login Connection을 확인해야 한다. GitHub 이메일 목록은 현재 CLI 인증 범위로 조회할 수 없었으며, 인증 범위를 임의 확대하거나 기존 이력을 다시 쓰지 않았다. noreply 주소 형식은 [GitHub 공식 기준](https://docs.github.com/en/account-and-profile/reference/email-addresses-reference)을 확인했다.

실행되지 않은 검증용 배포 2건은 정확한 ID와 alias 없음·BLOCKED 상태를 확인한 뒤 제거했다. 공통 결제 쓰기 환경변수는 0건이고 기존 Production 배포는 유지됐다. 예약 생성과 결제 상태 변경은 실행하지 않았다. 개발 DB의 사용자 6건, 예약 6건, 세션 2건, 원장 1건, 이벤트 4건, 관리자 감사 2건을 유지했고 예약·원장·이벤트 전체 비교값도 전후 동일했다.

계정 연결 문제를 해결하고 실제 HTTP·DB 결과를 확보하기 전에는 위 시나리오를 통과한 것으로 기록하지 않는다. 관리자 브라우저의 MFA·App Check 토큰 검증과 Production 운영 전환은 별도 범위로 유지한다.

## 2026-09-06 Vercel 소유권 이전

- 작업 목적: 개인 작업과 보들 배포 소유권을 분리하고 커밋 작성 계정과 배포 계정을 일치시킨다.
- 선택한 방식: 사용자 승인 후 기존 `bodeul-admin-web` 프로젝트를 보들 전용 Vercel 팀 `bodeul110`으로 이전했다. 개인 계정의 CLI 인증은 유지하고 보들 인증은 별도 `--global-config` 경로로 관리한다.
- 대안: 개인 계정의 GitHub 로그인 연결 교체, 커밋 작성자 변경, 새 프로젝트로 재구축은 선택하지 않았다.
- 선택 이유: 현재 MVP에서는 기존 프로젝트와 배포를 유지한 소유권 이전이 설정 재구축을 줄이고 다른 프로젝트의 인증에 영향을 주지 않는다.
- 리스크: 팀별 권한과 외부 연동은 별도 확인이 필요하다. 소유권 이전 성공만으로 새 배포 성공이나 결제 상태 전이 통과를 판단하지 않는다.

공식 이전 API의 요청·수락을 거쳐 보들 팀이 프로젝트를 소유하고 개인 팀 목록에서는 제거된 것을 확인했다. 이전 전후 프로젝트 ID, 환경변수 36개의 이름·대상 환경·보관 유형, 서비스 도메인, Git 저장소 연결, 배포 보호 설정, Production 배포 ID가 동일했다. 비밀값은 출력하거나 비교 문서에 저장하지 않았다.

기존 Production과 읽기 전용 Preview는 보들 계정에서 모두 `READY`로 조회됐고, 기존 서비스 주소의 비인증 HTTP 응답은 200이었다. 현재 프로젝트에 연결된 로컬 `.vercel/project.json` 두 곳의 팀 ID만 갱신했다. 요금제는 Hobby로 유지됐고 추가 결제·유료 기능 신청·약관 수락은 하지 않았다.

추가 확인으로 기존 읽기 전용 Preview를 보들 계정에서 재배포했다. [새 Preview 배포](https://vercel.com/bodeul110/bodeul-admin-web/GPSYLvNPmgdbM5afqLJ8KArHGniJ)는 `READY`이며, 생성 계정과 Git 작성 계정이 모두 `bodeul110`으로 확인됐다. 이 재배포에서는 기존 계정 불일치 차단이 재현되지 않았다. Production 배포를 교체하거나 결제 쓰기 플래그를 켜지는 않았다.

| 확인 대상 | 결과 |
| --- | --- |
| 기존 서비스 주소 `/` | 비인증 요청 200, 서비스 주소 유지 |
| 새 Preview `/` | 비인증 요청 302, Vercel 인증 경로로 이동 |

CLI `curl` 명령이 전역 옵션을 잘못 전달해 실패하여, CLI가 생성한 [공식 자동화 인증 헤더](https://vercel.com/docs/deployment-protection/methods-to-bypass-deployment-protection/protection-bypass-automation)를 검증 대상 Preview의 GET 요청에만 사용했다. 인증값은 메모리에서만 다루고 출력·파일·URL에 남기지 않았으며, 리디렉션을 따라 전송하지 않았다. Deployment Protection 설정은 유지했다.

이번 작업에서는 Firebase 사용자 인증값이나 앱 쓰기 요청을 보내지 않았다. Production DB 연결, 앱·서버 코드와 DB 데이터도 변경하지 않았다. 위 합성 결제 상태 전이, 관리자 브라우저의 MFA·App Check 검증과 Production 운영 전환은 수행하지 않았으며, 소유권 이전과 읽기 전용 배포 확인 결과로 대신하지 않는다.

## 2026-09-06 실제 결제 상태 전이 검증

사용자가 계정 이전 후 막혔던 검증을 이어가도록 요청했다. 위 소유권 이전 확인과 달리, 이번 단계에서는 실제 개발 Firebase 기준선 계정으로 인증하고 새 합성 예약 두 건의 상태를 API로 변경했다. 은행 송금이나 실제 환불은 실행하지 않았다.

### 실행 경계

- 제품 코드는 병합된 웹 `4cc45dd`와 동일하며, 검증 배포의 Git 메타데이터는 문서 작업 커밋 `4f1fcac`이다. 앱·서버 코드, 의존성, DB schema·권한은 변경하지 않았다.
- `vercel deploy --dry --json`에서 Next.js 소스 119개와 `.vercel` 제외를 확인했다. 인증 파일이나 로컬 환경변수 파일은 업로드하지 않았다.
- 별도 Preview `dpl_9Mvsft3uZJGUBCSwcvC3KsrY9yfH`에만 `--env ADMIN_BANK_TRANSFER_WRITES_ENABLED=true`를 전달했다. 공통 환경변수 36개에는 쓰기 플래그를 추가하지 않았다. [Vercel 배포 단위 환경변수](https://vercel.com/docs/cli/deploy#env)를 사용했다.
- 배포가 `READY`이고 보들 팀 소유·Preview인 것을 확인했다. 개발 계정의 인증, 기존 합성 원장의 일치, 신규 예약의 개발 DB 반영을 확인한 뒤 상태 전이를 시작했다.
- 검증기는 저장소 밖에서 실행했다. 요청 전에 예약 생성 ID·작업 ID·본문을 로컬 기록에 남겼고, 발급받은 Firebase ID token과 Vercel 자동화 인증값은 메모리와 정확한 대상의 HTTP 헤더에만 전달했다. DB 직접 쿼리는 `READ ONLY` 트랜잭션의 조회에만 사용했다.

| 양쪽 서버 결과 | 환자 Core API 조회와 관리자 API 조회의 최종 상태·버전 일치 |
| 응답 캐시 | 점검한 JSON 응답은 모두 `Cache-Control: no-store` |

검증 중 최초 기대값 한 건을 바로잡았다. 예약이 취소됐다는 이유만으로 검토 상태의 입금자명 정정까지 `409`로 예상했지만 실제 응답은 `200`이었다. 기존 V22 `set_bank_transfer_depositor`, Core API 계약 문서, Android `BankTransferPayment.canEditDepositorName()` 모두 결제 상태 `AWAITING_DEPOSIT`·`REVIEW_REQUIRED`에서 정정을 허용한다. 따라서 제품 동작이나 정책을 바꾸지 않고 검증 기대값을 기존 계약에 맞췄다. 해당 작업 ID의 정정 이벤트가 정확히 한 건이고 예약은 여전히 취소 상태임을 확인한 후, 새 입금자명으로도 입금 확인은 거부되고 환불만 가능한지 추가 검증했다. 최초 불일치와 재확인 기록은 로컬 실행 기록에 남겼다.

### DB와 종료 확인

| 항목 | 시작 전 | 종료 후 | 설명 |
| --- | ---: | ---: | --- |
| 사용자 | 6 | 6 | 기존 행 비교값 동일 |
| 예약 | 6 | 8 | 새 합성 예약 두 건만 추가 |
| 동행 세션 | 2 | 2 | 기존 행 비교값 동일 |
| 결제 원장 | 1 | 3 | 새 예약별 원장 하나씩 추가 |
| 결제 이벤트 | 4 | 16 | 정상 5건, 취소 후 검토·환불 7건 추가 |
| 관리자 감사 | 2 | 27 | 기존 원장 사전 조회 1건, 새 예약 조회 18건·변경 6건 추가 |

새 예약 두 건을 제외한 사용자·예약·세션·원장·이벤트의 전체 행 비교값은 전후 동일했다. 기존 원장 사전 조회 감사 1건이 추가된 시점을 기준으로 나머지 감사 행도 동일했다. 새 예약의 관리자 변경 감사는 각각 3건이며, 동일 작업 ID의 이벤트·변경 감사 중복은 0건이었다. 합성 원장·이벤트·감사는 삭제하지 않았다.

쓰기용 임시 배포는 정확한 ID·프로젝트·소유자·Preview·alias 없음 확인 후 제거했고 재조회에서 `404`를 확인했다. 기존 읽기 전용 Preview `dpl_GPSYLvNPmgdbM5afqLJ8KArHGniJ`에서 두 예약 모두 조회 `200`, 쓰기 `423 payment_writes_disabled`를 재확인했다. Production 배포 ID, Deployment Protection, 공통 환경변수는 유지했다.

이번 결과는 실제 Firebase ID token → Vercel 관리자 서버/Core API → 개발 PostgreSQL 경계의 검증이다. 실제 관리자 브라우저의 MFA·App Check 토큰 발급·검증, Production 전환과 실제 계좌 운영 검증은 포함하지 않는다. 이 기록만으로 메인 #27 전체를 완료 처리하지 않는다.
