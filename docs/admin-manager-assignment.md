# 관리자 웹 매니저 배정

## 설계 판단

- 작업 목적: 별도 도우미 없이 예약 코드 검색부터 매니저 배정까지 관리자 웹에서 처리한다.
- 선택한 방식: 기존 관리자 인증과 PostgreSQL 조회 권한으로 예약 버전·매니저 목록을 읽고, 기존 `assign_companion_session` 함수로만 배정한다.
- 대안: 브라우저 직접 DB 쓰기, Core API 프록시, 별도 시연 전용 배정 경로는 사용하지 않는다.
- 선택 이유: 현재 MVP 규모에서는 기존 관리자 서버와 감사·동시성 검증을 재사용하는 편이 운영 경계를 늘리지 않는다.
- 리스크: 후보 목록은 Core DB의 `MANAGER` 역할 기준이며 심사 승인·근무 일정·거리 기반 자동 추천이 아니다. 담당자가 별도로 확인한 매니저를 선택한다.

## 계약과 범위

- `SUPER_ADMIN`, `OPERATIONS`만 조회·배정할 수 있다. Firebase ID token, MFA, App Check 설정을 그대로 적용한다.
- 정확한 예약 코드 조회의 감사·분당 제한을 유지한다. 배정에 사용할 예약 상태와 버전은 같은 DB 행에서 읽는다.
- 후보 목록은 이름·이메일 검색, 최대 50개와 추가 결과 여부만 반환한다. 전화번호·Firebase UID는 반환하지 않는다.
- 배정 확인에는 예약 코드·환자·병원·일시·매니저를 표시한다. 예약 버전은 사용자가 입력하지 않는다.
- 중복 제출을 막고, 충돌 또는 응답 불확실 시 예약 재조회 전까지 추가 제출을 막는다. 자동 재시도하지 않는다.
- DB 함수의 예약 상태·버전·중복 세션·무통장입금 확인 및 감사 기록 검증을 우회하지 않는다.
- DB migration, IAM, DB 권한, 의존성, 운영 배포는 변경하지 않는다. 카드 예약에는 무통장입금 관리 패널을 표시하지 않는다.

## 기존 프로필 호환

- 실제 개발 데이터에서 기존 Core 매니저 3명의 이름·이메일이 비어 있는 것을 확인했다. 임의로 DB를 덮어쓰지 않고, 기존 프로필 원본의 표시 정보를 읽어 보완한다.
- Core DB에서 `MANAGER`로 조회된 UID에 대해서만 기존 Firestore 읽기 전용 경로로 `name`, `email` 두 필드를 조회한다. 원본 서류·전화번호는 읽거나 반환하지 않는다.
- 이름·이메일 보완 후 검색·정렬하며, 응답에는 Core UUID와 표시 정보만 포함한다. Firebase UID와 서류 심사 상태를 배정 권한으로 사용하지 않는다.
- 기존 OIDC의 개발 Preview/dev 브랜치 제한과 legacy 자격 증명 검증을 유지한다. 조회 감사를 남긴 뒤에만 응답하며, 조회·감사 실패는 503으로 종료한다.
- 현재 MVP에서는 Core 후보를 최대 1,000명까지 읽어 완전한 이름 검색을 제공한다. 이를 초과하면 일부 목록을 전체처럼 보이지 않도록 실패 처리하며, 프로필을 PostgreSQL로 이전하고 검색 인덱스·페이지 탐색을 추가해야 한다.

## 검증

- 단위 테스트 200건: 기존 배정 계약, 후보 조회 인증·역할·MFA·App Check 거부, 입력 길이·응답 검증, 상태·버전 조건, 이름 누락 표시와 기존 프로필 검색 보완.
- lint, Next.js 빌드, Vite rollback 빌드, 빌드 산출물의 인증 거부 경로 27건, GitHub CI·CodeQL·Vercel 검증을 통과했다.
- 로컬 브라우저에서 격리된 API 응답으로 선택 전 비활성화, 확인 취소, 정상 배정 1회, 예약 버전 전달, 완료 후 재배정 차단, 409 충돌·통신 실패 후 재조회 필요 상태를 확인했다.
- 390px 모바일 화면에서 가로 넘침 없이 선택·메모·오류 문구가 표시된다.
- 위 격리 테스트는 실제 DB 배정을 검증한 결과가 아니다. 아래 개발 환경 리허설을 별도로 수행했다. 운영 환경은 검증 대상이 아니다.

## 개발 환경 리허설

2026-10-29, PR #102와 #103을 `dev`에 병합하고 Vercel Preview가 `f59e520`을 배포한 뒤 확인했다. 실제 배정은 관리자 웹의 선택·확인 버튼으로 수행했으며, 배정 도우미나 직접 SQL을 사용하지 않았다.

| 구간 | 확인 결과 |
|---|---|
| 환자 앱 | Galaxy S24(Android 16)에서 가상 예약 신규 접수. 카드 체험 40,000원이며 실제 결제 없음 |
| 관리자 웹 | 예약 코드 검색, 매니저 이름 검색·선택, 예약 정보 확인 후 배정 HTTP 201 |
| 배정 결과 | 예약 `REQUESTED → MATCHED`, 버전 `0 → 1`, 담당 매니저 이름 표시, 중복 배정 버튼 제거 |
| 매니저 앱 | 동일 예약 코드·방문 일시·가상 시연 표식 확인. 기존 병원 가이드 7단계 진행과 최종 리포트 제출 |
| 종료·전달 | 예약·세션 `COMPLETED`, 단계 `7/7`, 환자 리포트 HTTP 200. 실제 환자 앱에서도 완료 상태와 작성 내용을 확인 |
| 관리자 재조회 | 동행 중·완료 상태가 반영되며 신규 배정 차단 유지 |
| 기존 데이터 | 시연 전후 다른 14개 예약의 상태·버전·매니저 ID 불변 |

비밀값과 실제 인물 정보가 섞일 수 있는 원본 화면·응답은 공개 저장소에 올리지 않는다. 개발 환경의 가상 예약 1건과 해당 세션·리포트, 기존 감사 기록만 변경했다. 운영 환경·DB 스키마·IAM·의존성·Android 코드는 변경하지 않았다.

## 시연 순서

1. 개발 환자 앱에서 신규 예약을 접수하고, `일정·이력 → 해당 예약 상세 → 예약 기본 정보`의 예약 코드를 확인한다.
2. 개발 관리자 웹의 `개발 환경 / Preview` 표시를 확인하고 `예약 검색`에서 코드를 입력한다.
3. 환자·병원·일시와 `매칭 대기 / 미배정` 상태를 대조한다.
4. `매니저 배정`에서 이름 또는 이메일을 검색하고 매니저를 선택한다. 필요한 경우 배정 메모를 입력한다.
5. `매니저 배정`을 누르고 확인창의 예약·매니저 정보가 맞으면 확정한다. 완료 메시지와 매칭 완료 상태·매니저 이름을 확인한다.
6. 매니저 앱에서 동일 예약을 열어 가이드를 진행하고 리포트를 제출한다. 환자 앱과 관리자 웹을 다시 조회해 완료 상태를 확인한다.

배정 결과가 불확실하거나 충돌하면 재전송하지 말고 같은 예약 코드를 다시 검색한다. 완료한 예약을 초기화하지 않고 다음 시연에서는 새 가상 예약을 접수한다.

## 남아 있는 제한

- 후보는 Core DB의 매니저 역할 기준이다. 이번 작업은 자동 매칭·근무 가능 시간 검증·신규 매니저 심사 승인 기능을 추가하지 않는다.
- 시연 병원은 기존 7단계 가이드이며 일부 앱 화면의 11·13단계 표시는 재사용된 화면 제목이다. 최신 13단계 전체 검증으로 해석하지 않는다.
- 기존 프로필의 이름 보완은 관리자 웹 범위다. 환자 앱에서는 같은 담당자를 일반 문구인 `배정 매니저`로 표시하는 기존 제한이 남아 있다.
- 무통장입금 미확인·이미 배정·종료된 예약의 DB 거부 계약은 유지했다. 이번 실환경 쓰기 시연은 카드 체험 예약으로 한정했다.
