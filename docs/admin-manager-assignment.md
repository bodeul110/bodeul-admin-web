# 관리자 웹 매니저 배정

## 설계 판단

- 작업 목적: 별도 도우미 없이 예약 코드 검색부터 매니저 배정까지 관리자 웹에서 처리한다.
- 선택한 방식: 기존 관리자 인증과 PostgreSQL 조회 권한으로 예약 버전·매니저 목록을 읽고, 기존 `assign_companion_session` 함수로만 배정한다.
- 대안: 브라우저 직접 DB 쓰기, Core API 프록시, 별도 시연 전용 배정 경로는 사용하지 않는다.
- 선택 이유: 현재 MVP 규모에서는 기존 관리자 서버와 감사·동시성 검증을 재사용하는 편이 운영 경계를 늘리지 않는다.
- 리스크: 후보 목록은 Core DB의 `MANAGER` 역할 기준이며 심사 승인·근무 일정·거리 기반 자동 추천이 아니다. 담당자가 별도로 확인한 매니저를 선택한다.

## 계약과 범위

- `SUPER_ADMIN`, `OPERATIONS`만 조회·배정할 수 있다. Firebase ID token, MFA, App Check 설정을 그대로 적용한다.
- 정확한 예약 코드 조회의 감사·분당 제한을 유지한다. 배정에 사용할 예약 상태와 버전은 같은 DB 행에서 읽는다.
- 후보 목록은 이름·이메일 검색, 최대 50개와 추가 결과 여부만 반환한다. 전화번호·Firebase UID는 반환하지 않는다.
- 배정 확인에는 예약 코드·환자·병원·일시·매니저를 표시한다. 예약 버전은 사용자가 입력하지 않는다.
- 중복 제출을 막고, 충돌 또는 응답 불확실 시 예약 재조회 전까지 추가 제출을 막는다. 자동 재시도하지 않는다.
- DB 함수의 예약 상태·버전·중복 세션·무통장입금 확인 및 감사 기록 검증을 우회하지 않는다.
- DB migration, IAM, DB 권한, 의존성, 운영 배포는 변경하지 않는다. 카드 예약에는 무통장입금 관리 패널을 표시하지 않는다.

## 기존 프로필 호환

- 실제 개발 데이터에서 기존 Core 매니저 3명의 이름·이메일이 비어 있는 것을 확인했다. 임의로 DB를 덮어쓰지 않고, 기존 프로필 원본의 표시 정보를 읽어 보완한다.
- Core DB에서 `MANAGER`로 조회된 UID에 대해서만 기존 Firestore 읽기 전용 경로로 `name`, `email` 두 필드를 조회한다. 원본 서류·전화번호는 읽거나 반환하지 않는다.
- 이름·이메일 보완 후 검색·정렬하며, 응답에는 Core UUID와 표시 정보만 포함한다. Firebase UID와 서류 심사 상태를 배정 권한으로 사용하지 않는다.
- 기존 OIDC의 개발 Preview/dev 브랜치 제한과 legacy 자격 증명 검증을 유지한다. 조회 감사를 남긴 뒤에만 응답하며, 조회·감사 실패는 503으로 종료한다.
- 현재 MVP에서는 Core 후보를 최대 1,000명까지 읽어 완전한 이름 검색을 제공한다. 이를 초과하면 일부 목록을 전체처럼 보이지 않도록 실패 처리하며, 프로필을 PostgreSQL로 이전하고 검색 인덱스·페이지 탐색을 추가해야 한다.

## 검증

- 단위 테스트 195건: 기존 배정 계약, 후보 조회 인증·역할·MFA·App Check 거부, 입력 길이·응답 검증, 상태·버전 조건, 이름 누락 표시.
- 로컬 브라우저에서 격리된 API 응답으로 선택 전 비활성화, 확인 취소, 정상 배정 1회, 예약 버전 전달, 완료 후 재배정 차단, 409 충돌·통신 실패 후 재조회 필요 상태를 확인했다.
- 390px 모바일 화면에서 가로 넘침 없이 선택·메모·오류 문구가 표시된다.
- 위 격리 테스트는 실제 DB 배정을 검증한 결과가 아니다. 개발 배포 후 실제 웹·앱 연결을 별도로 확인한다. 운영 환경은 검증 대상이 아니다.
